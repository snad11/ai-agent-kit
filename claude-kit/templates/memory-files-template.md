# Memory files template

**This file documents the memory file shape that the bootstrap process creates for each new project.** Memory lives at `~/.claude/projects/<project-key>/memory/` and is auto-loaded into every Claude Code session in that project.

The bootstrap process creates these files based on what it learns from the user during the bootstrap conversation + the audit pass.

---

## Files created at bootstrap

### 1. `MEMORY.md` — the index

Always loaded first. Lists all other memory files with one-line descriptions.

```markdown
# Memory index

## User
- [User profile](user_<name>.md) — role, preferences, working style

## Project
- [{{PROJECT_NAME}} scope](project_scope.md) — what the platform is, target users, business model
- [{{PROJECT_NAME}} features (MVP + amendments)](project_features.md) — confirmed product decisions
- [Vendor & infrastructure stack](project_vendors.md) — confirmed vendors (DB, hosting, third-party services)
- [Audit findings — repo summary](project_audits.md) — high-level audit summary, critical findings

## References
- [Project docs](reference_docs.md) — paths to client/spec docs, what each contains
- [Skills and rule file](reference_commands.md) — `/x-implement`, `/x-prompt`, etc. + master `.claude/rules.md`

## Feedback
- [Confidential material handling](feedback_confidentiality.md) — if applicable
- [Seniority context, code style, error handling, prompt generator workflow](feedback_seniority_and_workflow.md) — operating mode (auto-included from kit)
```

---

### 2. `feedback_seniority_and_workflow.md` — operating mode (auto-included)

This file is the SAME for every project bootstrapped from the kit. It documents:

- Senior architect/full-stack/UI-UX/DBA operating mode
- SOLID + DRY + reuse-before-create + no-over-comments principles
- ISO 27001 + OWASP awareness
- User-friendly error handling philosophy
- Workflow: read context BEFORE writing code
- PG / `/x-implement` / `/x-prompt` triggers and the 3-phase model
- Persistence rule (save new rules/preferences immediately)

The bootstrap copies this file from `claude-kit/templates/feedback_seniority_and_workflow.md` (see below) into the project's memory.

---

### 3. `project_scope.md` — what the project is (filled by bootstrap conversation)

Generated during bootstrap by asking the user:

- What is this project?
- Who are the users?
- What problem does it solve?
- What's the business model (if applicable)?
- What's MVP vs Phase 2?

Stored as a project-type memory.

---

### 4. `project_features.md` — confirmed product decisions

Generated during bootstrap by asking the user:

- What are the core features?
- Which are MVP?
- Are there any features that look like best practice but are intentionally NOT being implemented (e.g. "no escrow", "no subscription tiers")? These become "amendments" — the kit's audit and rules need to know about them.
- Any non-obvious decisions or amendments to default best practice?

This file becomes the source of truth for "what the project IS doing vs ISN'T doing".

---

### 5. `project_vendors.md` — confirmed vendor/infra stack

Generated during bootstrap by asking the user:

- DB? (Postgres / MySQL / MongoDB / Neon / Planetscale / Supabase)
- Hosting? (Hetzner / Contabo / Vercel / Railway / Fly / AWS)
- Auth? (custom / Auth0 / Clerk / Supabase Auth / Firebase Auth)
- Email? (Resend / Mailgun / SendGrid / Maileroo / Postmark)
- SMS / OTP? (Twilio / Arkesel / MessageBird)
- Payments? (Stripe / Paystack / Flutterwave / mobile money)
- Push notifications? (Firebase / OneSignal / native APN/FCM)
- Monitoring? (Sentry / Signoz / Datadog / Better Stack)
- Storage? (S3 / R2 / Backblaze)
- CDN?

Plus reality status: which are actually procured + working vs which are TODO.

---

### 6. `project_audits.md` — high-level audit summary pointer

Generated AFTER the audit pass completes. Contains:

- Path to the audit folder
- Summary of repo counts + finding counts
- Top critical findings (across all repos)
- Cross-cutting themes
- "How to apply" notes for future sessions

---

### 7. `reference_docs.md` — project doc paths

Generated by asking the user:

- Are there any spec docs? (PDF, MD, Notion exports?)
- Where do they live?
- Are they confidential?

If yes, the bootstrap can optionally run a spec extraction pass (see `audit-prompt.md` for the pattern).

---

### 8. `reference_commands.md` — skills + rules + scripts pointer

Auto-created from a template. Documents:

- The 6 skills installed (`/x-implement`, `/x-prompt`, `/x-rules`, `/x-check`, `/x-check-file`, `/x-add-rule`)
- The PG shorthand
- The decision tree (when to use which command)
- Layered enforcement (L1-L4)
- Where the rules file is
- How to extend the system

---

## After bootstrap — adding new memory files

The user (and Claude during sessions) should add memory files as new context emerges:

- New decisions made → save to `project_features.md` or a new `project_<topic>.md` file
- New behavioral preferences → save to `feedback_<topic>.md`
- New external doc references → update `reference_docs.md`
- Always update `MEMORY.md` index when adding a new file

---

## Memory location convention

Each project gets its own memory folder, named after the project's path with slashes replaced by dashes:

- Project at `/Users/mac/Projects/myapp` → memory at `~/.claude/projects/-Users-mac-Projects-myapp/memory/`
- Project at `/Users/mac/Projects/client/website` → memory at `~/.claude/projects/-Users-mac-Projects-client-website/memory/`

The bootstrap process auto-detects the path and creates the memory folder.

---

## The seniority memory file (auto-copied from the kit)

The `feedback_seniority_and_workflow.md` file is the same across all bootstrapped projects. The kit ships a master version at `claude-kit/templates/feedback_seniority_and_workflow.md` that the bootstrap copies into each new project's memory.

If you update the master, re-running the bootstrap on any project will refresh that file (with `--force-memory` flag — without it, existing memory files are preserved).
